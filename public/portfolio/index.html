01휴대폰 개통 신청(MNO) 내재화외부 링크 상품을 자체 신청 서비스로, 단통법 폐지 대응과 레거시 이관
Vinu Labs (univstore.com) · 2025.03 ~ 현재 · 설계를 주도하고 백엔드, 운영 어드민, 배치를 구현

배경

제가 맡기 전까지 휴대폰은 제휴 상품이었습니다. 고객이 누르면 중계업체 사이트로 넘어가는 외부 링크였고, 그 뒤로는 우리가 볼 수 있는 게 없었습니다. 고객이 정말 우리 사이트를 거쳐 개통했는지 확인할 방법이 없었고, 매달 중계업체가 보내 주는 결과를 그대로 믿을 수밖에 없었습니다.

신청 내재화

신청을 우리 서비스 안으로 옮겼습니다. 상품 노출과 신청서는 우리 사이트에, 접수부터 개통·배송 처리는 판매처(대리점)가 쓰는 판매처 관리 화면에, 지원금과 요금제 관리는 운영 어드민에 만들었습니다. 이제 신청 한 건 한 건이 우리 데이터로 남고, 접수·보류·배송·개통 상태가 바뀔 때마다 기록됩니다. 판매처가 한꺼번에 처리할 수 있도록 상태 변경과 송장 등록은 엑셀 일괄 업로드로도 받았습니다.

이렇게 쌓인 데이터 위에서 가족 개통, 30·36개월 할부 같은 기능을 하나씩 더할 수 있었습니다.

단통법 폐지 대응

가장 힘들었던 건 단통법 폐지였습니다. 오픈을 한 달 앞두고 지원금 정책이 바뀐다는 이야기를 들었는데, 어떤 지원금으로 바뀌는지는 물론 지원금 이름조차 나중에 정해진다고 했습니다. 판매처를 통해 들은 통신 3사의 이야기도 서로 달랐습니다.

그래서 확정될 때까지 기다리지 않고, 정책과 상관없이 필요한 지원금 관리 화면과 엑셀 일괄 등록부터 만들었습니다. 7월 22일 시행 당일에는 "공시지원금"을 "공통지원금"으로 바꿨습니다. 그다음 2주 동안 하나였던 지원금을 가입 유형별(번호이동·기기변경·신규가입)로 나눠 테이블, 엑셀 양식, 가격 계산, 화면을 다시 맞췄습니다.

커밋과 회의록 날짜 기준

레거시의 한계와 이관

MNO를 처음 얹은 웹은 회사 초창기에 만든 레거시였습니다. Node 서버가 Handlebars로 화면까지 그렸고, 한 레포에 프론트와 백엔드가 규격 없이 섞여 있어 하나를 고치면 다른 곳이 깨졌습니다.

레거시 웹신규
구조Node + Handlebars, 프론트·백엔드가 한 레포API 서버(NestJS, 도메인 계층 분리)와 프론트 분리
MNO 이후 기능수정할 때마다 사이드 이펙트가족 개통(2026.01), 30·36개월 할부(2026.10)를 신규 API 위에 추가

옮길 때 원칙은 하나였습니다. 레거시의 동작이 정답이라는 것. 노션에 기능을 하나하나 분류해 목록을 만들고, 제가 맡은 항목은 레거시 코드와 직접 대조했습니다. 비교용 AI 스킬도 함께 썼습니다. 그 결과 사전신청 하나에서만 네 가지 차이를 찾았습니다. 예를 들어 고객이 옵션을 고르지 않으면 레거시는 상품의 기본값을 채워 넣는데, 신규 API는 그대로 빈 값을 저장하고 있었습니다. 세 가지는 레거시와 같게 고쳤고, 나머지 하나는 비교 문서에 남겼습니다.

전환은 2026년 웹 전체 개편과 함께 트래픽 10%부터 단계적으로 넘겼고, 개편 QA 731건 중 약 230건을 맡아 처리했습니다.

결과와 회고

MNO는 지금 연 매출 약 3~4억 원 규모이고, 올해 가족 개통을 도입한 뒤 매출이 약 10% 늘었습니다.

아쉬운 점은 할부 계산입니다. 백엔드는 모노레포였고 공통 모듈도 서브모듈로 함께 쓰고 있었지만, 할부 계산은 당시 일정에 맞춰 신규 API, 고객 화면, 운영 어드민, 리포트에 각각 따로 만들었습니다. 그러다 보니 리포트 금액이 2~3원 어긋나는 일이 생겼습니다. 메시지 시스템에서는 SDK 패키지로 계약을 공유했던 것처럼, 할부 계산도 공통 모듈이나 패키지로 빼서 프론트와 백엔드가 같은 코드를 쓰게 했다면 더 좋았을 것 같습니다.

02멀티채널 메시지 발송 시스템SQS + BullMQ, 전용 DB 분리, 아웃박스와 멱등
Vinu Labs (univstore.com) · 2026.09 ~ 10 · 설계 및 구현

배경

고객에게 가는 알림은 주문·배송·인증·CS·재입고 같은 정보성 안내부터 마케팅까지 전부 문자(SMS/LMS)로 나가고 있었습니다. 2026년 상반기에만 132만 건, 약 3,200만 원이었습니다. 대량 발송은 Lambda가 수신자 목록을 청크로 잘라 큐에 넣는 방식이었고, 중계사를 부르는 코드는 서비스 여러 곳에 흩어져 있었습니다.

가장 큰 문제는 보낸 결과를 저장하지 못한다는 점이었습니다. 누구에게 무엇이 나갔고 실제로 도착했는지 알 수 없었고, 그래서 실패하면 문자로 대신 보내야 하는 알림톡 같은 채널을 붙일 수가 없었습니다.

요구사항

회사는 정보성 알림을 알림톡(건당 24.5원 → 3.8원)으로, 광고를 브랜드메시지로 바꿔 연 2,000만~2,500만 원을 줄이려 했고, 다음 해에는 CRM 자동화도 예정돼 있었습니다. 그래서 채널 전환에 앞서 발송 시스템부터 다시 만들기로 했고, 아래를 기준으로 잡았습니다.

  • 문자, 알림톡, 브랜드메시지, 이메일을 하나의 요청 형식(SDK)으로 보낸다
  • 수신자 한 명 단위로 상태(발송·성공·실패)와 실제로 나간 채널을 남긴다
  • 20만 명 캠페인을 20분 안에, 중계사 한도(초당 800명) 안에서 보낸다
  • 재시도나 배포 중 재시작에도 중복·누락이 없다
  • 요청하는 서비스와는 레포와 DB를 나누고, SDK로만 연결한다

Kafka 대신 SQS + BullMQ

처음 비교한 건 Kafka였습니다. 처리량과 재처리(리플레이)는 Kafka가 낫지만, 우리 규모에서 필요한 처리량은 초당 잡 4개 수준이었습니다. 반면 재시도, 지연, 우선순위, 속도 제한은 Kafka에서는 직접 만들어야 하고, 클러스터는 쓰지 않아도 비용이 나갑니다.

외부 서비스와의 경계는 SQS로, 내부 단계 사이는 BullMQ로 정했습니다. 대신 중복 방지와 오토스케일 지표는 우리가 직접 책임지기로 했습니다.

중계사 제약

중계사(NHN Cloud)는 요청당 1,000명까지 받고, 콜백에 우리가 보낸 데이터를 돌려주지 않습니다. 그래서 요청할 때 넣은 그룹 키로 결과를 다시 이었고, 발송과 콜백 해석은 중계사별 어댑터에 넣어 중계사를 바꾸거나 추가해도 요청 형식과 SDK는 그대로 두었습니다.

구조

  1. 서비스는 SDK로 발송 요청을 SQS에 넣습니다. 대량·예약 발송은 배치가 500건씩 나눠 넣습니다.
  2. service가 요청을 받아 이력을 남기고, 수신자 200명 단위 잡으로 나눠 BullMQ에 넣습니다.
  3. processor가 중계사 한도 안에서 보냅니다. 요청 자체가 실패하면 바로 실패 결과로 돌려보냅니다.
  4. 중계사의 결과 콜백은 webhook이 서명만 확인하고 큐에 넣습니다. 콜백이 몰려도 DB는 영향을 받지 않습니다.
  5. service가 수신자별 상태를 확정하고, 결과를 SQS로 요청한 서비스에 돌려줍니다.

DB 분리

메시지 시스템은 기존 운영 DB와 완전히 떨어진 전용 DB를 씁니다. 캠페인 한 번이면 수신자 수만큼 결과 행이 생기고 콜백이 올 때마다 갱신되는데, 이 쓰기가 주문·결제가 도는 운영 DB에 섞이지 않게 하려는 것이었습니다. 두 DB는 서로 조회하지 않고 SQS로만 이어집니다.

아웃박스와 멱등

서비스 쪽은 아웃박스 패턴으로 요청 유실을 막았습니다. 주문 같은 도메인 트랜잭션 안에서 발송 요청 행을 먼저 기록하고, 커밋한 뒤에 보냅니다. 보내기 전에 앱이 죽거나 SQS 접수가 실패해 남은 요청은 배치가 1분마다 찾아 다시 보냅니다(5분 경과, 최대 5회, 회차는 MySQL 락으로 하나만). 메시지 시스템이 멈춰도 영향은 그 발송뿐이고 다른 API는 정상입니다.

다시 보내면 같은 요청이 두 번 갈 수 있어서, 메시지 시스템은 (요청 서비스, 요청 ID) 유니크 키로 한 번만 받고 잡 ID도 요청에서 결정적으로 만들어 재시작 뒤 다시 넣어도 같은 잡이 되게 했습니다. 수신자마다 발급한 메시지 ID 하나로 요청부터 중계사 결과까지 조회합니다.

03이벤트 파이프라인과 Snowflake 적재Kinesis 수집, DMS CDC 무중단 교체, dbt
Vinu Labs (univstore.com) · 2026.05 ~ · 설계 및 구축

배경

사용자 행동 로그는 레거시 웹 서버가 Firehose로 보내 Redshift에 주기적으로 적재하는 구조였습니다. 이벤트 정의가 서버, 프론트, 분석 쪽에 흩어져 있어 같은 행동을 서로 다르게 기록했고, 새 프론트를 만들면서 이벤트를 SDK 하나로 모으고 수집 경로도 새로 짜기로 했습니다.

위는 행동 이벤트 수집 경로, 아래 초록은 운영 DB 변경분(CDC) 적재 경로입니다.

설계 판단

  • Firehose 앞에 Kinesis. Firehose에 바로 넣으면 버퍼링 정책이 곧 수집 정책이 됩니다. 스트림을 두고 7일 보관해 유실을 막고, 나중에 다른 소비자를 붙일 수 있게 했습니다.
  • 수집 서버(event-api)를 API 서버와 분리. 분석 이벤트는 일부 유실이 허용되지만 결제는 아닙니다. 같은 자원과 처리량 제한을 나눠 쓰지 않게 했습니다.
  • 게이트웨이는 1차 검증만. 본검증까지 하면 스키마가 바뀔 때마다 수집 서버를 배포해야 하고, 그 사이 이벤트가 버려집니다.
  • S3는 Parquet와 원본 JSON 두 벌. Athena는 읽은 바이트로 과금되니 분석용은 Parquet로, 원본은 재처리용 보험으로 둡니다.

2026년 5월 가동 후 하루 약 164만 건(평균 초당 19건, 피크 29건)이 들어오고, 피크 때도 Kinesis 처리 용량의 5%가 안 됩니다.

Snowflake로 모으기

분석 환경은 Redshift(월 약 65만 원)를 중간 저장소로 쓰고 있었는데, 회사 전체 분석을 Snowflake로 모으기로 하면서 S3까지는 안정적으로 쌓고 그 뒤는 Snowflake가 가져가는 구조로 정리했습니다. 운영 DB의 변경분도 DMS CDC로 Snowflake에 넣고 dbt로 정리했습니다.

운영 중인 CDC 태스크 무중단 교체

파트너사 교환권 번호가 개인정보로 분류되면서, 주문 CDC가 이 값을 웨어하우스에 평문으로 쌓고 있다는 게 문제가 됐습니다. 컬럼을 빼는 매핑 변경은 실행 중인 태스크에 적용되지 않아서 새 태스크로 넘겨야 했습니다.

  • 기존 태스크를 특정 커밋 시각에 멈추고, 새 태스크를 같은 시각부터 시작해 이어 붙였습니다(매핑 규칙 163개).
  • 되돌릴 수 있는 기한을 "정지 시각 + binlog 보관 72시간"으로 못 박고 복구 지점을 기록했습니다.
  • 경계 앞뒤 5분 중복 0행, 경계 이후 반영 정상을 확인했습니다.
  • 이미 쌓인 값은 S3 파일 242개와 Snowflake 원본 2,379행에서 지우고, dbt 모델에서도 빼 다시 들어오지 않게 했습니다.

상품 데이터 추가와 LLM 분류 격리

상품 자동 분류에 필요한 카테고리·브랜드·옵션 등 테이블 11개를 새 CDC 태스크로 추가했습니다. 넣기 전에 DMS 인스턴스의 7일 최저 여유 메모리를 확인했고, 1회 풀로드 225,370행이 원본 개수와 모두 일치하는 것을 본 뒤 dbt 모델 55개와 지연 알람을 붙였습니다.

상품 분류는 Snowflake 안에서 LLM을 부르는데, 이게 실패하면 매시 돌던 전체 적재까지 멈추고 연속 실패 시 태스크가 자동 정지되는 구조였습니다. 분류 빌드를 별도 태스크로 떼어 적재와 분리했고, 후보 모델 12개를 정답을 숨긴 300건으로 비교해 정확도를 유지하면서 1,000건당 비용을 10.41 → 7.47 크레딧(약 28%)으로 낮췄습니다.

다음 과제

11월에 행동 이벤트 경로 전체를 다시 점검해 보니, 전송 실패 알람이 없고 실패한 이벤트를 다시 보내지 않으며(fire-and-forget), 개발 환경 설정이 운영 스트림을 가리키는 문제가 있었습니다. 내년 광고·CRM으로 이벤트를 더 많이 쓰게 되는 만큼, DLQ와 중복 제거, 환경 분리를 먼저 넣으려고 합니다.

에브리타임 웹뷰 자동 로그인

우리 쇼핑 화면은 에브리타임 앱 안의 웹뷰로도 열립니다. 이 경로에서는 로그인 화면 없이 항상 자동으로 로그인돼야 하는데, 2026년 6월 웹 전체를 새 프론트로 옮기면서 이 동작을 다시 만들어야 했습니다.

세션이 없는 채로 들어오면 에브리타임 인가 서버로 보내고, 돌아온 인가 코드를 서버에서 토큰으로 바꿔 프로필을 받은 뒤 가입하거나 로그인시킵니다. 웹뷰 전체를 대상으로 잡으면 카카오·네이버 웹뷰에서도 리다이렉트가 걸릴 수 있어서, 앱 User-Agent를 에브리타임, 대학백과, 자사 앱으로 나눠 판별하게 바꿨습니다. 이후 대학백과 앱에서 에브리타임 로그인이 뜨던 문제도 이 구분으로 해결했습니다.

  • 재가입 제한 회원의 가입을 거절할 때 에브리타임 쪽 연동을 풀지 않아, 다음 시도에서 제3자 제공 동의 화면이 건너뛰어지던 문제를 찾아 레거시와 같게 연동 해제를 호출하도록 고치고 테스트를 붙였습니다.
  • 회원 식별자(uid)가 없는 기존 회원은 로그인 시점에 채우되, 동시에 두 번 로그인해도 하나만 생기도록 조건부 UPDATE로 막았습니다.

대학백과 SSO

고등학생이 많은 대학백과 앱 사용자를 예비 대학생 회원으로 받기 위해 대학백과 SSO를 붙였습니다. 브라우저에 시크릿을 둘 수 없는 앱 웹뷰라 PKCE 방식으로 로그인하고, 가입 직후 본인인증, 파트너용 연동 상태 API, 탈퇴·가입 실패 시 연동 해제를 만들었습니다. IP 허용, API 키, OAuth 시크릿은 상대 회사 개발자와 맞춰 개발·운영 환경에 반영했습니다.

배포 후 13일 동안 대학백과 계정 가입이 222명이었고 그중 128명이 고등학생 인증을 마쳤습니다. 고등학생 인증 회원의 일평균 순증은 15.2명에서 24.4명으로 늘었습니다.
