[뭉치](/posts/2026-09-22-mungchi-intro/)의 설치 파일을 처음 남에게 건넸더니 Windows가 "알 수 없는 게시자"라고 물었다.
답은 안다. 코드 서명을 하면 된다. 그런데 서명이 뭔지 설명해 보라고 하면 못 했다.

이상한 일이다. 백엔드 개발자로 일하면서 서명은 매일 봤다. 결제사 웹훅의 `X-Signature` 헤더, JWT의 세 번째 토막, AWS 요청에 붙는 SigV4, git 커밋의 Verified 배지.
전부 라이브러리가 해 줬고, 나는 검증 함수가 `true`를 돌려주는지만 봤다. 이번에 처음부터 다시 봤다.

## 서명이 답하는 질문은 둘이다

서명은 메시지에 붙는 짧은 값이고, 받는 쪽이 두 가지를 확인하게 해 준다.

- **무결성**: 보낸 뒤로 한 글자도 안 바뀌었는가
- **인증**: 내가 생각하는 그 상대가 보낸 것이 맞는가

서명은 **내용을 숨기지 않는다.** 이걸 암호화와 섞어서 알고 있었다. JWT의 페이로드는 base64일 뿐이라 누구나 읽는다. 서명은 "읽지 못하게"가 아니라 "고치지 못하게"다.

출발점은 해시다. SHA-256 같은 해시 함수는 아무 길이의 입력을 고정 길이 값으로 바꾸고, 입력이 한 비트만 달라도 값이 완전히 달라진다.
하지만 해시만 붙여서는 아무것도 못 막는다. 중간에서 내용을 고친 사람이 해시도 다시 계산해서 붙이면 된다.
**해시에 "그 상대만 가진 것"을 섞어야 서명이 된다.** 무엇을 섞느냐로 두 종류가 갈린다.

## 비밀을 나눠 가지면 MAC, 키를 둘로 나누면 전자서명

**메시지 인증 코드(MAC)** 는 보내는 쪽과 받는 쪽이 같은 비밀을 갖는다. 가장 흔한 것이 HMAC이다. 비밀과 메시지를 함께 해시한다.
받는 쪽은 같은 비밀로 같은 계산을 해서 값이 같은지 본다.

**전자서명(digital signature)** 은 키가 한 쌍이다. 개인키로 서명을 만들고 공개키로 검증한다. 공개키로는 서명을 만들 수 없다.
RSA, ECDSA, Ed25519가 여기에 든다. 큰 파일을 통째로 서명하지 않고, 먼저 해시한 뒤 그 해시에 서명한다.

"개인키로 암호화한 것이 서명"이라는 설명을 오래 믿고 있었다. RSA에서는 비슷하게 들어맞지만 ECDSA나 Ed25519에는 암호화라는 연산이 아예 없다. 서명은 서명이라는 별개의 연산이라고 보는 쪽이 맞았다.

둘의 차이는 하나로 줄어든다. **검증할 수 있는 사람이 위조도 할 수 있는가.**
MAC은 검증하는 쪽도 같은 비밀을 가졌으니 같은 서명을 만들 수 있다. 그래서 둘 사이에서만 의미가 있고, 제3자에게 "이건 저쪽이 보낸 것"이라고 증명하지 못한다.
전자서명은 검증하는 쪽이 공개키만 가지므로 위조할 수 없다. 공개키를 세상에 뿌려도 된다. 나중에 "내가 보낸 게 아니다"라고 잡아떼기 어렵다는 성질(부인 방지)도 여기서 나온다.

이 기준으로 매일 보던 것들을 다시 놓았다.

| 매일 보던 것 | 종류 | 검증하는 쪽이 가진 것 |
|---|---|---|
| 결제사·GitHub 웹훅의 서명 헤더 | MAC (HMAC-SHA256) | 대시보드에서 복사해 온 웹훅 시크릿 |
| AWS 요청의 SigV4 | MAC (HMAC을 여러 번) | AWS가 보관한 내 시크릿 키 |
| JWT `HS256` | MAC | 발급 서버와 같은 시크릿 |
| JWT `RS256`, `ES256` | 전자서명 | 발급자가 공개한 공개키 (JWKS) |
| git 커밋의 Verified | 전자서명 | 내가 GitHub에 올려 둔 공개키 |
| TLS 인증서, exe 코드 서명 | 전자서명 | 운영체제에 들어 있는 루트 인증서 |

JWT 하나 안에 두 종류가 다 있다는 것이 제일 놀라웠다. `HS256`은 토큰을 검증하는 모든 서비스가 시크릿을 가져야 하고, 그중 하나가 털리면 누구나 토큰을 만들 수 있다.
`RS256`은 검증하는 서비스가 공개키만 가진다. 서비스가 여럿이면 후자를 쓰는 이유가 이것이었다.

코드 서명이 전자서명일 수밖에 없는 이유도 여기서 풀린다. 내 설치 파일을 검증할 사람은 세상의 모든 Windows PC다. 그 모두와 비밀을 나눠 가질 수는 없다.

## 검증하는 쪽에서 틀리기 쉬운 곳

공부하다가 내 옛 코드를 떠올리고 뜨끔했던 것들이다.

- **웹훅은 파싱하기 전의 원문 바이트로 검증한다.** JSON으로 파싱했다가 다시 직렬화하면 공백과 키 순서가 달라져서 해시가 안 맞는다. 프레임워크가 본문을 먼저 파싱해 버리면 원문을 따로 받아 둬야 한다
- **비교는 시간이 일정한 함수로 한다.** `===`는 앞에서부터 틀린 글자를 만나면 바로 끝난다. 응답 시간의 차이로 서명을 한 글자씩 맞혀 갈 수 있다. Node에는 `crypto.timingSafeEqual`이 있다
- **서명이 맞아도 옛날 요청일 수 있다.** 서명은 "언제"를 말해 주지 않는다. 가로챈 요청을 그대로 다시 보내는 것(재전송)은 서명을 통과한다. 그래서 타임스탬프를 서명 대상에 넣고 오래된 것은 버린다
- **JWT는 토큰에 적힌 알고리즘을 믿지 않는다.** 헤더의 `alg`를 `none`으로 바꾸거나, `RS256` 공개키를 `HS256`의 시크릿으로 쓰게 속이는 공격이 있었다. 검증할 때 허용할 알고리즘을 서버가 못 박는다

```typescript
const expected = createHmac('sha256', secret).update(rawBody).digest()
const given = Buffer.from(signatureHeader, 'hex')
const ok = given.length === expected.length && timingSafeEqual(given, expected)
```

여기까지 오면 질문이 하나 남는다. 전자서명은 공개키로 검증한다. 그런데 **그 공개키가 정말 그 사람 것인지는 누가 말해 주나.**
git은 내가 직접 GitHub에 올렸으니 된다. 세상의 모든 PC가 내 공개키를 알 방법은 없다. 다음 편이 그 이야기다.
